## 2. Post times: scheduled posts

On the two news channels, **25 of 30 posts were published 1.5 to 2.7 hours after their id was made**, at round times (on the quarter hour on one, every ten minutes on the other). They are scheduled posts: the id carries the **upload** time and `createTime` the **publish** time. On A3 and A4 the two agree within 15 s. The list is ordered by `createTime`.

So, for T8 and the crawler:
- The 365-day backfill stops by `createTime`, read from the items, not by id.
- **New posts are found by id, not by order.** A scheduled post can appear with an id older than posts already seen, so a "newest id seen" watermark would skip it.
- "Within 3 hours" counts from `createTime`, when the post became public.

## 3. What the probe misread (fixed in M1f)

1. **The walk repeated the first page.** The probe took the next cursor from the answer's `cursor` field, which the `creator` list does not have. So it asked for the newest page 40 more times: each account's "615 posts" were its first 15, 41 times over. The summary's 2,419 posts were **59 unique posts**, and its oldest date and id-time counts came from repeats. **Fix:** the next cursor is the page's oldest `createTime` (`ttclient.NextCreatorCursor`); posts are kept once by id; an empty page steps back a week (yt-dlp reports the list answers about a week before its cursor); a page with nothing new stops the walk ("stuck"). The fake TikTok now answers without a cursor too, so the tests catch this.
2. **The empty account answer counted as answered** (above). **Fix:** the decoder reads an empty `userInfo` or `itemInfo` as a refusal.
3. **Page timings were 0** for plain-HTTP page loads. **Fix:** timed.

## 4. What the second run adds (M1f)

The first run left four things unexplained. The second run records each one:

- **Is a browser page refused too, or only tks's URLs?** The browser step now records **the page's own API calls**: the post list the profile page asks for when it loads, after one scroll if needed. Then it follows a post's link and records the **comments that page asks for itself**. Then it asks for the next page of each, from the page, with the page's own parameters. This is the "browser for everything" fallback (methods.md §3). It also records which query parameters the page sends that tks does not, what the page sees (`navigator.webdriver`, time zone, screen), and the browser page's bytes. Chrome now starts without its automation flag.
- **How far back does the list go?** A depth check reads one `creator` page at 30, 90, 180, 365 and 730 days back for each test account, which the time cursor allows without walking. In the full pass, one read at 365 days per account.
- **The largest page size:** `count` 16 and 20 are tried as well as 5 and 30.
- **Video 403:** the probe records which cookies the identity sends to the video host, keeps the refusal's body, and tries two more ways: Chrome's `<video>` request headers (same-site, `Range`, the site as referer), and the post page's own video link.
- The walk's page cap for the test pass rises from 40 to 60, so A3 is read to its first post (580 videos at 14 per page) and posts read can be compared with the account's `videoCount` (T30).

## 5. What it means so far

- **The post list and the accounts work with plain HTTP and no signatures.** The `creator` list needs no cookies, no device id and no `msToken`, and its cursor is a time that works from any identity. This covers the daily account refresh (from the page), the 2 h 45 min new-post check, the metrics refresh and the 365-day backfill. Cost per list page: about **40 KB and 350 ms** for 15 posts.
- **Comments need something else.** TikTok refused them unsigned, and refused tks's page-signed URLs. The second run shows whether the page's own comment calls are answered. If they are, comments come through browser pages (about 6.6 MB per profile page load with media blocked; the second run measures the cheaper follow-up post page). If not, comments are not available logged out from this exit, and the scope is the owner's decision (methods.md §7).
- Pinned posts: the `creator` list has no pinned flag. If the page's own list shows `isPinnedItem`, the flag comes from there (one browser call per account and day); if not, objective §2's pinned flag is not available.
- No sign yet of T29 (device ids burnt): the repeats were the probe's own bug.
