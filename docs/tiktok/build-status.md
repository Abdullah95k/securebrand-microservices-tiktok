## Standing instructions (owner, 2026-11-06, with the master session's review request)

1. Don't rename or remove topics, event fields, schemas or endpoints others use. Additions are fine; tell the owner about any change.
2. Don't register `securebrand.content.*` in any Schema Registry shared with another service until the master publishes v1. (tks's `securebrand.common.v1` clashes with igs's, so tks registers nothing in a shared registry either.)
3. **Nothing on the shared pilot server** (the droplet the Phase 0 and probe runs used): no browsers, long runs or installs, without the owner's approval.
4. Keep this file current: the master reads it.
5. Answer the master's requests with downloadable files, synthetic examples only.
6. Plain language; one command per code block; Iraq time (UTC+3); never ask for credentials; never log or commit secrets or real data; don't circumvent bot checks (**tks's signer is the owner's exception**, 2026-11-06: see Decisions); keep all data; propose, then build.

## Findings

From M9c1 (2026-11-05, no TikTok request; from the load and soak runs against `fakett` on this session's 4-CPU machine):
- **A rename could cost a post's comments for a whole comment window.** A comment or reply task starts its identity on the post's page under the name the account's list had; after a rename that page did not load (in `fakett`; TikTok's answer is T38), and the task retried five times into the dead letter queue, so the job ended `partial`. It now stops at once and marks the post for a whole read by the next check, which carries the new name; nothing fails.
- **The soak confirms the store converges on the world** (A6) through restarts, faults and every kind of change, once the comment windows have run: tks re-reads a post's comments only when its count goes up and its window allows (ADR 0007 §4), so a deletion on a post whose count then falls, or comments on a post read within its window, wait for a later read by design. The soak's final walk comes a week on for that reason.
- **Metrics rows need their daily partitions ahead of time.** A capture whose day has no `post_metrics` partition is skipped silently; the leader creates 14 days ahead every run, so this only bites if the leader is down for two weeks. The soak keeps them ahead on `fakett`'s clock.
- **The pipeline's own ceiling is far above what tks needs**: 30 accounts of 60 posts (1,800 posts, 65,667 comments and replies, 98 % of the 14,828 calls signed) backfilled at once in 18 s, with the store equal to the world; the persister writes 11,700 new comment rows a second and passes over 19,800 unchanged ones. TikTok's tolerance and the signer's pages (C4), not the pipeline, set tks's pace. The thread stage's backlog grows first (peak 4,867 tasks).

From M9b2 (2026-11-05, no TikTok request; from the code and the smoke run against `fakett`):
- **A deployed crawler would never have signed a call.** The signer started Chromium from `tt.browser.binary` alone, empty by default, so every signer page failed to open (`exec: no command`) and no comment or reply was read; the bootstrap fallback looked up `$TKS_BROWSER_BINARY` and `PATH`, the signer did not. Every earlier run set the binary explicitly (tests, the probe, Phase 0, the signer pilot), which hid it; the chart's smoke run with the browser image found it. The signer now finds Chromium as the fallback does, with a regression test.
- **Three lag alerts could never have fired.** The alerts copied from fbs selected fbs's consumer groups (`tks-crawler-*`, `tks-persister`); tks's are `tks-tt-crawler-<stage>-<lane>` and `tks-tt-persister`, which the leader does publish. Crawlers idle with work waiting, on-demand checks waiting and the persister falling behind would have gone unseen. Fixed, with a test that every group an alert or a KEDA trigger names is one of tks's.
- **The whole chart runs as rendered.** Its hooks and nine Deployments, under the pods' hardening (non-root, read-only root, every capability dropped, memory limits), migrate, create the topics, import three accounts through the API and finish their backfills against `fakett` with posts, comments, replies and media stored and no error logged. CI also runs it with the browser image, `fakett` requiring signatures: the crawlers' Chromium pages, sandbox off, sign every comment and reply.
- **tks has no DLQ replay.** fbs's `fbctl dlq replay` was never ported; dead-lettered tasks are harmless (the next scheduled check reads the account again) and quarantined records stay 7 days in `tks.persist.dlq`. Added to M9c.

From M9b1 (2026-11-05, no TikTok request; from the code, C4's figures and the owner's prices):
- **At C4's figures tks is under the budget**: per 1,000 accounts a day, 2 IPs ($0.20), 16.3 browser hours ($0.28), compute ($0.20) and 174 GB stored ($0.58) make about $1.26, **$0.00126 per account** against $0.0019. Storage is nearly half and only grows (D8), so the cost per account rises with time unless accounts grow too; the alert at 90 % ($0.00171) is the early warning.
- **Pausing backfills lowers little of a fixed cost.** IPs, compute and storage do not fall when backfills stop; browser time and new storage do. A pause therefore holds new accounts and their first reads (and discovery's entry checks) until the cost per account falls under 95 % of the budget, which more checked accounts or a raised budget bring about; it never touches the checks.
- **A pause used to cost checks**, found while building this: a due metrics walk (daily back 30 days, weekly back 365 days) runs in the backfill lane and stands in for the check, so any budget pause (the request budget's too, since M6c) left those accounts unchecked until it lifted. Fixed: while paused, the check runs and the walk waits.

From M9a (2026-11-05, no TikTok request; from fbs's code and the tests):
- **The fixes fbs made for Facebook's walls help tks too, without those walls.** A restart used to start every identity again, each with a page load (~92 KB to 600 KB on the wire through the proxy, and a new `device_id` TikTok has not seen). Identities now outlive restarts and rolling updates, so a deploy costs no burst of page loads.
- **fbs's later fixes are all in now** (fbs main `4816736`), except Facebook's own (mentions, keyword search, the pilot) and fbs's raise of requests per identity to 1500–3000, which answered Facebook's walls on page loads; TikTok walled none in C2, C3 or C4, so tks keeps 400–800 until the canary or the measurements say otherwise.
- **A closed job's tasks used to keep cycling.** The reaper closed a stalled job but left its tasks on the retry topics, where they kept running for a job that was over; it now cancels the job, and the task topics keep a day (as long as a job lives) instead of three.

From M10b (2026-11-05, no TikTok request; from the design and the tests against `fakett`):
- **Most discovery calls are guesses until C6** (T36): only search and the feed were recorded. The probe therefore does not trust its own operation seed: it tries each call both ways, records where the posts and people were in each answer (`data.item`, `itemList`, `userList`, `user_list`) with the answer's top-level keys, and captures the calls TikTok's own page makes on each page. M12 and M13 take the endpoints, parameters and parsers from that.
- **The signer page's location may matter for search.** The crawler opens signer pages on a profile (`open_on: profile`, S2); the probe also signs search and the feed on their own pages, so C6 says whether a profile page's signature is accepted for them (T32 only covered comments on another account's page).
- **"Same results as from Iraq?" is measured indirectly.** The exits are served `region: US`; the probe reads one list page of 30 found authors and counts those with a post made in Iraq, and the post languages per source. Compared with the owner's recording from Iraq (Arabic 56 of 141 posts), this tells whether Iraqi keywords from a US exit still lead to Iraqi accounts (§8.3); if not, exits near Iraq are the owner's proxy decision (§16 item 1).

From M6b (2026-11-01, no TikTok request):
- **TikTok's ids do not fit a JavaScript number** (post ids are above 7 × 10¹⁸), so the API gives every id as a string. A client that parsed them as numbers would join the wrong posts silently.
- **An account is also a person**: its user id is the key of its comments on other accounts' posts. So erasing an account also redacts what it wrote elsewhere and suppresses it as an author; otherwise its replies on monitored posts would survive the request.
- **An erased account cannot be recognised by its name afterwards**, because the erasure deletes the names. A request to read it by username runs and writes nothing (the crawler and the persister drop it by user id); by `id:` it is refused (409).
- **Mentions of an erased person are cleared where tks can find them cheaply** (the posts that mention them, the comments of posts they commented on), as fbs does; a mention in another comment is cleared when that comment is next written. A full scan of every comment would make each erasure cost as much as the comment table.
